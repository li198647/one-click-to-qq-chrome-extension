# 一键发到 QQ

在浏览器里选中一段文字，按一下快捷键，**内容就发到你手机 QQ 上了**。

核心场景：在电脑浏览器里看到一段文字或一个链接（商品页、文章、地址、验证码），想立刻在手机上打开或存下来 —— 不用切窗口、不用拖文件、不用扫码。

---

## 架构

三段式，缺一不可：

```
┌─────────────────┐      HTTP       ┌──────────────┐    WebSocket    ┌──────────────┐
│  Chrome 扩展     │ ─────────────→ │   本地桥      │ ─────────────→ │  QQ 开放平台  │
│  （浏览器里的入口）│  127.0.0.1:18761│  （Python）   │   长连接        │  官方机器人   │
└─────────────────┘                 └──────────────┘                 └──────┬───────┘
                                                                            │
                                                                     你的手机 QQ
```

- **Chrome 扩展**只负责「读内容」和「给你一个浏览器里的入口」。
- **本地桥**是跑在你自己电脑上的 Python 小程序，通过 QQ 官方机器人开放平台收发消息。
- 浏览器出于安全沙箱，**没有任何一条路能直接碰到 QQ**，所以中间必须有一个本地程序当桥。

## 为什么这么设计

| 方案 | 结论 |
|---|---|
| **本方案：官方机器人 + 本地桥** | ✅ 采用。不碰 QQ 通信协议、不动桌面客户端、**零封号风险**，也不依赖桌面是否解锁 |
| UI 自动化（模拟键鼠操作桌面 QQ） | ❌ 否决。QQ NT 是 Electron，聊天区 UIA 树读不到输入框；且要求桌面必须解锁、窗口不能在屏幕外 |
| 第三方协议（NapCat / OneBot） | ❌ 否决。属非官方协议，主号有封号风险 |
| 网页版 QQ | ❌ 不可行。`web.qq.com` / SmartQQ 已于 2019-01-01 停运 |
| 飞鸽 / Syncthing | ❌ 不适用。它们没有浏览器里的入口，而"入口"正是这个项目的全部价值 |

## 下载安装（给使用者）

**不想看源码、只想装上用** → 去 [Releases](https://github.com/li198647/one-click-to-qq-chrome-extension/releases) 下载现成的 zip：

| 文件 | 内容 | 什么时候下 |
|---|---|---|
| `one-click-to-qq-extension-vX.Y.Z.zip` | 只有浏览器扩展 | 已装过桥，只想更新扩展 |
| `one-click-to-qq-kit-vX.Y.Z.zip` | 扩展 + 本地桥 + 完整说明 | **第一次装，选这个** |

两个包解压后都带一份 `!安装说明-先看这个.txt`，照着走即可。核心只有两步：**解压到一个不会被挪走的文件夹** → `chrome://extensions` 开开发者模式 → 「加载已解压的扩展程序」。

> ⚠️ **为什么不是 `.crx`**：Chrome 自 2018 年起禁止安装非应用商店来源的 `.crx`（双击提示"可能已损坏"，拖进扩展页也会被拦）。「解压 + 加载已解压的扩展程序」是目前唯一可行的本地安装方式。
>
> ⚠️ **解压出来的文件夹不能删、不能挪**，它是扩展本体，删了扩展就失效。

### 怎么打出这两个包（维护者）

> 📌 **打包是按需的，不是每个版本都打。** 常规的版本递增（改代码、修 bug）**只需要提交并推送代码**：`git commit` → `git tag` → `git push origin main` + `git push origin <tag>`。只有明确说"要打包 / 出下载包 / 发 Release"时才跑下面的脚本。理由：zip 里装的是"当时那版代码的快照"，代码一改它就过时，平时攒着只是噪音；真要用的时候再打，反而一定是新的。

```powershell
powershell -ExecutionPolicy Bypass -File tools\make-release-package.ps1
```

脚本会从 `extension/manifest.json` **读出版本号**（不硬编码），把两个 zip 生成到 `dist/`，然后**解压回来逐项复检**：敏感文件（`config.json` / `state.json` / 日志 / `__pycache__`）、明文密钥（AppSecret / AppID / openid）、扩展 9 个必需文件是否齐全。任一中招就直接报 FAIL 并让脚本以非 0 退出。

```powershell
# 然后到网页上建 Release 并上传 dist\ 里的两个 zip：
# https://github.com/li198647/one-click-to-qq-chrome-extension/releases/new
```

Release 的描述文案存在 `packaging/Release说明-vX.Y.Z.md`，直接复制粘贴。

## 快速开始

### 第 1 步 · 准备一个 QQ 机器人

1. 打开 <https://q.qq.com/> → 注册（**个人主体**即可，身份证 + 手机 + 人脸，不需要企业资质）
2. 创建机器人 → 记下 **AppID**，生成 **AppSecret**（⚠️ 只在生成时明文显示一次）
3. 左侧「**开发设置**」→ 找到「**开发体验号码设置**」→ 点「+ 添加用户」→ 填**你自己的 QQ 号** → 保存后扫码把机器人加为好友
   - 旧文档里这一步叫「开发管理 → 沙箱配置 → 消息列表配置」，新版已改名
4. 手机 QQ 的消息列表里会出现你的机器人 → **给它发一句话**（桥需要靠这句话拿到你的 openid）

> 「服务范围 → 好友（私聊）→ 允许被其他 QQ 用户添加使用」**保持关闭**即可。关闭时管理员和开发体验成员仍可添加，正是自用所需。
>
> 「服务器 IP 白名单」**不用填**。官方文案：未设置时所有来源 IP 都会被允许调用。

### 第 2 步 · 启动本地桥

```bash
cd bridge
# 把 config.example.json 复制成 config.json，填入 appid 和 secret
python qq_bridge.py
```

依赖：`pip install qq-botpy Pillow`（Python 3.8+）

> `Pillow` 从 `1.0.1` 起用于**发图片**：探测真实格式、超 20MB 缩尺寸、原格式被拒时转 PNG。**没装也能正常启动**，只是发图时会给出明确的错误提示（文字那条路完全不受影响）。

启动成功后日志会显示：

```
[botpy] 机器人「你的机器人名」启动成功！
[botpy] 心跳维持启动...
本地服务已启动: http://127.0.0.1:18761
```

**这个桥要一直开着。** 桥关了就发不出去。

> 💡 `1.0.6` 起它会**缩到系统托盘**：起来之后那个黑窗口就不见了，任务栏右下角多一个企鹅图标。要停桥，在托盘图标上**右键 → 退出（关掉桥）**；想临时看日志，右键 → 显示日志窗口。这么设计是因为控制台窗口的 X 只能"关掉"、改不成"最小化"（原因见下面「开发笔记」里那一节），所以干脆把 X 摘掉、把窗口藏起来，让托盘成为唯一的出口。

> 💡 `1.0.4` 起，**重启电脑后不用再去磁盘里翻这个文件了**：打开扩展弹窗，连不上桥时状态行右边会出现一个「**启动本地桥**」按钮，点一下就把它拉起来。
>
> 首次启动桥时它会**自己把自己登记好**（写一份宿主清单 + 往注册表登记三处），所以你一次都不用选文件。万一哪天 `bridge` 文件夹被搬了位置、或者登记被清理软件删了，双击 `bridge\重新登记.bat` 补一次即可。
>
> ⚠️ 装/更新到 `1.0.4` 后，`chrome://extensions` 点「重新加载」时浏览器会提示**新增了一项权限**（`nativeMessaging`，就是"允许扩展跟本地程序对话"），点确认即可 —— 不确认的话扩展会处于停用状态。
>
> 不想留着登记项时，卸载方式是删掉注册表里这三处（都在当前用户下，不需要管理员权限）：`HKCU\Software\Thorium\NativeMessagingHosts\com.mumu.qq_bridge`、`HKCU\Software\Google\Chrome\NativeMessagingHosts\com.mumu.qq_bridge`、`HKCU\Software\Chromium\NativeMessagingHosts\com.mumu.qq_bridge`，再删掉 `bridge\com.mumu.qq_bridge.json`。

### 第 3 步 · 装 Chrome 扩展

1. 地址栏输入 `chrome://extensions`
2. 右上角打开「**开发者模式**」
3. 左上角点「**加载已解压的扩展程序**」→ 选中 `extension` 文件夹
4. 去 `chrome://extensions/shortcuts` 确认 `Ctrl+B` 已分配
   - ⚠️ 未打包的开发版扩展，manifest 里的默认快捷键**不会自动生效**，需要在这里手动设一次
5. ⚠️ 扩展需要「在所有网站上运行」的权限（用于监听网页里的复制）
   - `0.1.3` 起，点「重新加载」后扩展会**自己给已经开着的标签页补装监听**，不用再手动刷新每个标签页
   - 唯一的例外：标签页里如果还留着**更早版本**的监听器（重载前就已打开），它虽然听得到复制但发不出消息。**刷新一次该页面**即可彻底干净
   - 弹窗最底部写着当前版本号，用它确认自己加载的是不是最新版

## 用法

### 快捷键发送

按下 `Ctrl+B`，内容按三级优先级自动选取：

| 优先级 | 来源 | 说明 |
|---|---|---|
| ① | **选中的文字** | 在页面上划选一段文字，**不需要先 Ctrl+C** |
| ② | **剪贴板** | 没有选中内容时，读剪贴板 |
| ③ | **页面标题 + 链接** | 前两者都空时，发当前页面的标题和 URL |

**快捷键永远发最新那条**（候选列表的第 1 项），不受弹窗里选择的影响 —— 因为没有界面可以挑。

### 点图标：先看再发，还能改选

点扩展图标会打开一个弹窗，**上下两块，刻意分开**：

```
一键发到 QQ                    [ 立即发送 ] ← 按钮在标题行最右端
● 一切正常，可以发送
┌─ 将要发送 · 来自剪贴板 ─────────────┐
│ ┌────────────────────────────────┐ │ ← 线框里只有"这一下会发出去的
│ │ https://item.taobao.com/item…  │ │   那一段文字"，和下面候选分开
│ └────────────────────────────────┘ │
└────────────────────────────────────┘
候选 · 最近 4 条          点一行改成发那条
1  https://item.taobao.com/item…     ← 深色 = 当前选中（和上面框里是同一段）
2  商品已下架，客服说换这个链…
3  483920
4  https://www.zhihu.com/question/…
快捷键 Ctrl + B 永远发最新那条，这里的选择不影响它。
```

- **上面那块 = 已经定下的内容**：框里的字就是这一下会发出去的（来源可能是「选中文字」「剪贴板」或「页面标题+链接」）
- **下面那块 = 可以挑的候选**：最多 4 条，第 1 条永远是最新那条
- **点任意一行即可改选**；选中行底色变深，**上面的框和右上角按钮的文案会同步变**（按钮变成「发送第 N 条」）—— 免得选中了第 2 条、按钮却还写"立即发送"
- 发送按钮是 **Windows 对话框「是 / 否」那种小尺寸**（88 × 26，字号 12px），放在标题行最右端 —— 发送是这个弹窗唯一的主动作，但不值得用一整个通栏去强调它
- 「共 N 字」那行提示**已去掉**。内容超过 20 字时 `…` 就是截断的记号；出错时的具体原因会直接写进红色的标题里，所以排查信息没有丢
- **鼠标悬停在框上或某一行上可以看全文** —— 只显示前 20 字时，光看开头可能认不出是哪一条
- 两块和真实发送走的是同一个取值函数（`background.js` 里的 `resolveContent()`），所以框里看到什么，发出去就是什么
- 每项只显示**前 20 个字**，后面用 `…` 收尾。20 字是特意选的：链接到第 20 字刚好露出域名（`https://item.taobao.…`），再短就只剩 `https://`，等于没显示
- 列表里只显示**开头**，发送的是**完整内容**，一个字都不会截
- 剪贴板里是图片时，「将要发送」那一块会换成**这张图的缩略图**（见下面的「发图片」）
- `chrome://` 开头的设置页、扩展商店、新标签页**读不到选中文字和标题**，但只要你先把内容复制进剪贴板，照样能发

### 一键启动本地桥（`1.0.4` 起）

重启电脑后桥不会自己跑起来。以前得去磁盘里翻 `bridge\start_bridge.bat`，日子久了必然忘记它放在哪 —— 所以现在连不上桥时，弹窗里会直接给你一个按钮：

```
一键发到 QQ                    [ 立即发送 ]
● 连不上本地桥         [ 启动本地桥 ] ← 只在"连不上桥"这一种状态下出现
```

点一下会发生什么：

| 阶段 | 屏幕上看到的 |
|---|---|
| 1 | 按钮变「正在启动…」并禁用，状态行写「正在启动本地桥…」 |
| 2 | 每 1.5 秒问一次桥起来没有；**秒数显示在按钮上**（`启动中…7s`） |
| 3 | 桥的本地服务应答了 → 状态行变「正在连接机器人…」，继续等机器人登录 |
| 4 | 全好了 → 绿色「一切正常，可以发送」，按钮消失 |

- **最多等 30 秒**（桥的本地服务）+ 20 秒（机器人登录）。等不到就把原因原样写在下面那行红字里，**不会假装成功**
- **桥起来之后会缩进系统托盘**（`1.0.6` 起）：窗口被藏起来、标题栏的 X 被摘掉，任务栏右下角留一个企鹅图标。退出走托盘右键 → 「退出（关掉桥）」；想临时看日志走托盘右键 → 「显示日志窗口」。窗口标题写的是「**这是转发QQ的桥文件，保持开启，最小化就好**」，一眼就知道那是什么、该不该关（提权启动时前面会多一串系统加的「管理员: 」）
  - 托盘图标**消失了**通常就意味着桥没了（进程结束，Windows 会自动清掉图标）—— 这时重新点一下弹窗里的「启动本地桥」即可
  - ⚠️ **万一托盘图标没挂上**（资源管理器异常之类），桥会**老老实实把窗口留在任务栏**，绝不做"藏了窗口又没有托盘"这种事 —— 否则就再也找不到退出入口了。这条有工具守：`tools/test_tray.py` 的第 3 段专门打桩验它
- **幂等**：桥已经在跑时点它不会起第二个（宿主会先探一下端口，直接回"已经在跑了"）
- 那个按钮**不会一直挂在那儿**：桥在跑但机器人没连上、缺 openid、正在检查——这几种状态下它点了也没意义，所以平时整条是隐藏的
- 按钮出现在状态行里，而状态行只有 272px 宽 —— 所以启动过程中的秒数写在了**按钮**上而不是状态行里（实测：写成「正在启动本地桥…已等 12 秒」只剩 10px 余量，字体一换就会掉成两行）。这条有工具守：`tools/measure-popup-row.py`

**它是怎么做到"扩展能启动本地程序"的**（扩展其实没有这个能力，走的是 Chrome 唯一的合法通道）：

```
扩展（点按钮）
  → chrome.runtime.sendNativeMessage('com.mumu.qq_bridge', {cmd:'start'})
    → Chrome 按注册表 → 找到 bridge\qq_host.bat → 拉起它
      → 它执行 qq_native_host.py
        → 先探 18761 端口在不在，不在才拉起 start_bridge.bat
```

其中"宿主在哪"这份登记信息由**桥自己**在启动时写好，所以不需要你去选任何文件。相关细节与两个坑见下面「开发笔记」。

### 发图片（`1.0.1` 起）

两个入口，都是一下：

| 入口 | 怎么用 | 适合 |
|---|---|---|
| **剪贴板里的图片** | 截图工具截个图（或网页图片上右键 →「复制图片」），然后**点扩展图标**或按 `Ctrl+B` | 截图、任意来源的图 |
| **右键网页图片** | 在网页图片上右键 →「**发送此图片到 QQ**」 | 网页上随手看到一张图想发走 |

**弹窗里会明确标出这一次要发的是图片**：

```
一键发到 QQ                    [ 立即发送 ]
● 一切正常，可以发送
┌─ 将要发送 · 来自剪贴板图片 ──────────┐
│ ┌──────────────────┐               │
│ │    （真缩略图）    │ ← 不是文字框   │
│ └──────────────────┘               │
│ 图片 · 1080×2400 · 2.4 MB · clip…  │ ← 尺寸与体积
└────────────────────────────────────┘
候选 · 最近 4 条          点一行改成发那条
1  ▨ 图片 · 1080×2400 · 2.4 MB         ← 小徽标 = 这条是图片
2  https://item.taobao.com/item…
```

规则和边界，**这几条都是被硬限制逼出来的**：

- **图片不进候选列表**（历史里仍然只有文字）。`chrome.storage.session` 只有 **10MB**，而 base64 要**膨胀 1/3** —— 4 张 2MB 的截图就把它撑爆了。撑爆不是"图片存不进去"这么客气，而是**整个历史写入失败**，连你攒的文字候选一起搞挂
- 剪贴板里**同时有图和文字**时（比如从网页复制"图 + 说明文字"），仍然**发文字** —— 不破坏已经在用的行为
- **20MB 以内原样发出**。超过 20MB 会被 QQ 降级成「文件卡片」（手机上要点开下载才看得见），所以桥会**自动缩一次尺寸**（长边 2560 → 1600 → 1024 逐级试），并且**只降分辨率、不换格式** —— 截图上的小字用 JPEG 压会糊，缩尺寸只是"变小"，字还是那个字
- 官方文档对图片格式的说法**自相矛盾**（一处写"只支持 png/jpg"，另一处写"支持 jpg/png/gif/webp/bmp"）。所以**先按原格式发，被拒了才转成 PNG 重试一次**。副作用：动图 GIF 万一走到转换，会变成静态图（只在真被拒时发生）
- 图片被缩过或转过格式时，**会弹一条通知告诉你** —— 悄悄改画质、悄悄把动图变静图，都不行
- ⚠️ **需要登录才看得到的网页图片，右键发不了**。Chrome 规定扩展后台发起的跨站请求**不带目标站的 cookie**，所以网盘、后台系统、私有仓库里的图会下载失败。这时会**明确报错**并让你改用「复制图片」，**绝不静默换成别的内容发出去**

> 发图比发文字慢一点：base64 让体积再涨 1/3，一张几 MB 的图，「一键」这一下大约要等 1 秒左右。
>
> 按 `Ctrl+B` 同样支持图片（剪贴板里是图就发图），保持"一键"的一致感。

### 候选列表从哪来

Chrome **不提供任何「剪贴板变了」的通知接口** —— 扩展**只能**在"能看见剪贴板"的瞬间读到它（详见下面的开发笔记）。所以历史靠四路一起攒：

| # | 来源 | 覆盖 |
|---|---|---|
| ① | 网页里的 `copy` / `cut` 事件（`content.js`） | ✅ 网页里 `Ctrl+C` / `Ctrl+X` ／ ✅ 右键 → 复制 / 剪切（**iframe 里也监听**） |
| ② | **切回页面 / 切回标签页**时拍一张剪贴板快照 | ✅ 在记事本、微信、截图工具里复制完，切回浏览器那一刻收进来 |
| ③ | 页面**有焦点时每 2 秒巡检一次**剪贴板 | ✅ 网页自带的「复制」按钮（走 `writeText()`，不触发 `copy` 事件） |
| ④ | 每次被触发时（点图标 / `Ctrl+B`）拍一张快照 | ✅ 兜住前面漏掉的一切 |

也就是说：**只要你在浏览器里复制过、或者复制完切回了浏览器，它就能攒住。**

规则：
- **相同内容不会重复留两份** —— 只把它移到最前
- 顺序按"复制 / 被观察"的时间倒序，**发送动作不影响顺序**
- **所有写入是串行的**（一条 Promise 链）—— `chrome.storage` 没有事务，同时到达的几次记录会互相覆盖
- **只存内存**（`chrome.storage.session`），**关掉浏览器就清空**，绝不把可能含密码/验证码的剪贴板内容写到磁盘上
- 弹窗里有「**清空历史**」，随时可以抹掉

> 巡检（③）每 2 秒读一次剪贴板，只在**当前页面持有焦点且可见**时才读 —— 页面切走后立刻停。如果你介意这个行为，把 `extension/content.js` 顶部的 `POLL_MS` 改成 `0` 即可关掉它（另外三路照常工作）。
>
> 候选没凑满 4 条时，弹窗底部会直接写明原因（`候选 2/4 条……`），不会让你以为功能坏了。
>
> 弹窗最底部还有一行小字：`记录来源：网页复制 ×3 · 定时巡检 ×2 · v1.0.0` —— 冒号后面是**每一路各记下了几条**，最后是当前版本号。复制完打开弹窗，如果「网页复制」还是 ×0，就说明前面那次复制没被听到（那是要排查的信号，不是正常状态）。

### 发送反馈

- 成功 → 扩展图标跳出**绿色 `OK`**（2.5 秒后消失）
- 失败 → 图标常驻**红色 `ERR`** + 系统通知写明原因（桥没启动 / 机器人没连上 / 具体报错）

**绝不假装成功。**

## 实测结论

### ✅ 带链接的消息能正常发出去

官方文档 8.3 节《消息URL白名单配置》写的是：机器人下发消息里的链接域名必须**提前报备**，且「域名需提前进行 ICP 备案」。第三方资料更直白地说含 URL 的消息会被**静默过滤**。

实测（`bridge/probe_url.py` 连发 5 种形态）结果：

| # | 形态 | 接口返回 | 手机是否收到 |
|---|---|---|---|
| 1 | 纯文本（对照） | 200 `ok=True` + msg_id | ✅ |
| 2 | `https://www.baidu.com` | 200 `ok=True` + msg_id | ✅ |
| 3 | `www.baidu.com` | 200 `ok=True` + msg_id | ✅ |
| 4 | `baidu.com` | 200 `ok=True` + msg_id | ✅ |
| 5 | 文字 + 淘宝链接 | 200 `ok=True` + msg_id | ✅ |

**5 条全部到达手机，且 URL 被 QQ 自动识别成可点击的蓝色链接** —— 那条"必须备案"的限制在**沙箱环境（未上架）下并未生效**。

> ⚠️ 这是腾讯当前的行为，策略可能变化。桥里保留了链接检测预警，一旦发链接开始失败你会立刻看到提示。

### ✅ 主动消息配额

官方 API 文档：**个人认证 = 单聊 1000 条 / 用户 / 天**（Bot 维度 10 qps，单关系 20 qpm）。

> 网上流传的"每月只有 4 条"是**误读** —— 那是"互动召回消息的 4 个时间周期"（当天 / 1-3 天 / 3-7 天 / 7-30 天），不是月配额。

| 限制 | 说明 |
|---|---|
| **必须先发过一句话** | 腾讯限制：只有你主动给机器人发过消息，它才能主动找你。openid 到手后写入 `state.json`，之后长期可用 |

## 开发笔记（踩过的坑）

### Chrome 没有"剪贴板变了"的通知 —— 这决定了历史功能只能这么做

想自动攒剪贴板历史，看起来有三条路，实际全是死的或半死的：

| 可能的办法 | 实际情况 |
|---|---|
| 后台静默轮询剪贴板 | ❌ `readText()` 要求文档有焦点，后台 service worker 和隐藏文档都没有（本项目在 0.1.1 已亲手撞过 `Document is not focused`）。**但在页面里（content script）、且页面有焦点时轮询是可行的** —— `0.1.3` 的第三路就是这么做的 |
| `chrome.clipboard.onClipboardDataChanged` | ❌ Chrome Apps 时代的遗留 API，扩展里拿不到；且拿到通知后还要靠 `document.execCommand('paste')` 取内容，那条老路同样受焦点限制 |
| `clipboardchange` 事件 | ⚠️ 仍在 origin trial 阶段（要申请令牌），且官方明确写「**只有在文档具有焦点时才会触发**」—— 后台照样收不到 |

**结论**：历史只能由扩展自己在"能看见的瞬间"攒 —— 有焦点的页面里的 `copy` / `cut` 事件与剪贴板巡检，加上"切回页面"和"被触发"这两个瞬间的快照。

### ⚠️ manifest 的 `content_scripts` 管不到"已经开着的标签页"

`content_scripts` 只在**页面加载时**注入。扩展一重载（点「重新加载」、或者升级），此刻已经开着的标签页里**就没有 `content.js` 了** —— 你在那些页面上怎么复制，扩展都听不见，表现的就像"历史功能坏了"。

`0.1.3` 之前，唯一的办法是手动刷新每个标签页，而这个动作看不见、容易忘。现在的做法是：`chrome.runtime.onInstalled`（装/升级/重载都会触发）+ service worker 冷启动时，用 `chrome.scripting.executeScript({ target: { tabId, allFrames: true }, files: ['content.js'] })` **主动给所有现有标签页补注入一次**，每个浏览器会话/版本只扫一次。

配套要点：
- `content.js` 必须自己处理"被注入两次"—— manifest 的自动注入和这里的补注入会重叠
- 补注入要逐个 `try` 住：`chrome://` 页面、扩展商店、被冻结/丢弃的标签页都会抛错，一个失败不能打断其余的

### ⚠️ 防重复注入**不能**用"标志位就 return"（0.1.3 的错误写法）

0.1.3 是这么写的：

```js
if (window.__qqSendSnifferReady) return;
window.__qqSendSnifferReady = true;
```

看着挺对，实际会**把整页监听变成哑的**：

1. 点「重新加载」刷新扩展；
2. 旧那份 content script 的**监听器还挂在页面上**（DOM 监听不会因为扩展重载消失），但它的 `chrome.runtime` 上下文**已经失效** —— 它照旧能听到 `copy` 事件，却再也发不出消息，复制被**静默吞掉**；
3. 新注入的脚本一进来就看见旧标志位是 `true`，直接 `return`，于是**什么都不装**。

净效果：**页面开着不动，就一直废着**，非得手动刷新页面才好。表现就是"连着复制 4 条、只留下最后 1 条"（那 1 条还是打开弹窗时读剪贴板读到的）。

**正确做法（0.1.4）**：新实例先把旧实例装的东西**全拆掉**，再重新装。

```js
if (typeof window.__qqSendSnifferTeardown === 'function') window.__qqSendSnifferTeardown();
// 自己统一用 on()/every()/later() 登记，全部推入 disposers，teardown 时逐个撤销
```

这样无论隔离世界是"同一个"还是"新建的"，结果都是**恰好一份、且上下文有效**的监听器。

### ⚠️ `chrome.storage` 没有事务 —— 并发"读-改-写"会互相覆盖

历史是"读出列表 → 改 → 写回"。这不是原子的：连着复制 4 条时，4 个 `clip-captured` 消息几乎同时到达（**service worker 刚从休眠被唤醒时最容易**，此时几条消息会挤在同一批里），4 次操作各自读到**同一份旧列表**、各自写回**自己那一份**，最后写入的把前面三个全盖掉 —— 表现同样是"只留下最后 1 条"。

这类 bug 还特别阴：**它是间歇性的**，SW 醒着时 4 次复制间隔通常远大于一次 storage 往返，一点事没有；只有挤在一起才复现。

**解法**：所有改动排进同一条 Promise 链，一次只跑一个。

```js
let storeChain = Promise.resolve();
function editStore(fn) {
  const run = storeChain.then(async () => {
    const st = await readStore();
    const out = await fn(st);   // fn 就地改 st
    await writeStore(st);
    return out;
  });
  storeChain = run.then(() => undefined, () => undefined);  // 一次失败不能掐断后面的
  return run.catch(() => []);
}
```

### 剪贴板历史存哪：`storage.session` 而不是 `storage.local`

剪贴板是你电脑上最敏感的地方之一（密码、验证码、别人私聊发你的东西都会经过它）。`storage.local` 会把内容**明文写进浏览器配置目录**并长期保留；本项目改用 `chrome.storage.session` —— **只在内存里，关掉浏览器即清空**。绝不用 `storage.sync`（那会把剪贴板同步到云端）。

MV3 的 service worker 随时会被回收（闲置约 30 秒），所以历史**不能放在模块级变量里**，必须走 `chrome.storage`。

### 图标：为什么不能做成"透明的黑企鹅"

工具栏图标**没法感知浏览器是浅色还是深色主题**。纯透明背景的黑色剪影在深色工具栏上会**直接消失**（`tools/icon_preview.png` 里 F 那一行就是这个反例）。所以图标带了一层**白色圆角底**，浅色深色都能看清。

尺寸给了 16 / 32 / 48 / 128 四档 —— **32 那一档是给高分屏工具栏的**，缺了它 Chrome 会把 16px 拉伸上去，边缘发虚。

造型上的取舍：QQ 那只企鹅是**正面圆胖、戴红围巾、眨眼**，所以这里刻意走**侧身几何剪影 + 外撇的翅**，不画围巾、不 wink，避免看起来像在模仿官方标志。多方案对比图用 `python tools/make_icons.py --preview` 出，换造型改 `draw_side()` 里的坐标即可。

### 改 UI 不用每次都去 `chrome://extensions` 点重载

`node tools/make-preview.js` 会生成 `tools/preview-popup.html`：它拿**真实的** `popup.html` + `popup.js`，只把 `chrome.*` 接口打桩喂假数据。所以**样式和渲染逻辑跟真身是同一份**，不会出现"预览好看、装上去不一样"。改完弹窗先看这个页面，确认了再去装。

### ⚠️ 发图片：官方接口那条路比看起来窄得多（`1.0.1`）

**① `post_c2c_file()` 用不了 —— 它不收 `file_data`。**
botpy 这个包装函数只认 `url` / `upload_id` / `file_name`，也就是只支持"腾讯自己去下载这个地址"或"分片上传"两条路。本机没有公网地址，`url` 那条实测回 **400「上传URL错误」**（回这句话恰好证明是**腾讯的服务器**去下这个地址）。分片上传能用，但要 4 次调用。所以桥里改成**自己发 HTTP 请求**、用 `file_data`（base64）直传，一次调用就拿到 `file_info`。

**② 但 `file_data` 在官方文档的请求体参数表里没写。**
实测能跑、能拿到 `file_info`、图能到手机，属于"**能跑但没承诺**"。哪天真被关掉，备用路径是改成分片上传。这条风险同时写在 `qq_bridge.py` 的注释里。

**③ `aiohttp` 默认只收 1MB 的请求体。**
一张 4MB 的截图转成 base64 就是 5.3MB —— 不把 `client_max_size` 放开，请求会被直接挡成 **413**，而且连日志里都看不出原因（连接层就被拒了，处理函数根本没被调用）。

**④ service worker 里没有 `FileReader`，也没有 DOM 的 canvas / Image。**
所以"字节 → base64"只能自己**分块** `btoa`（一次性 `String.fromCharCode.apply` 塞几百万个字节会直接抛 `RangeError`），拿宽高只能用 `createImageBitmap`。这几个恰好是后台 / 弹窗 / 网页三处**唯一都有的交集** —— `extension/imageutil.js` 就是按这个交集写的。

**⑤ 那个三处共用的文件必须写成 IIFE 挂 `globalThis`，不能有顶层 `const`。**
`content_scripts` 注入的脚本会被**反复注入**（扩展重载时 `injectIntoAllTabs` 会再来一遍），顶层 `const` 第二次注入就抛 `Identifier 'x' has already been declared`，整个脚本当场停摆。理由和 `content.js` 用 IIFE 完全一样。

**⑥ 扩展后台发起的跨站请求不带 cookie。**
所以"需要登录才看得到的图"右键发不了 —— 这是浏览器的安全边界，不是能修的 bug。碰到就明确报错、让人改用「复制图片」。同理 `blob:` 开头的地址也拿不到（那个地址只在页面自己的上下文里有效）。

**⑦ 图片不进历史的那个数字。**
`chrome.storage.session` 的配额上限是 **10,485,760 字节（10MB）**。如果按字面实现"图片也进候选列表"：4 张 2MB 的截图 = 原始 8MB → base64 后 **10.7MB** → 配额一爆不是"图片存不进去"，而是**整个历史写入失败**，连攒好的文字候选一起搞挂。所以图片只作为"本次要发的那一条"出现，历史里仍然只有文字。

### ⚠️「选中文字」是个**持续状态**，不是一次动作（`1.0.2` 修的 bug）

按"**谁存在**"排优先级会踩坑。现象（木木报的）：

```
复制图片        → 弹窗里有缩略图   ✓
复制一段文字    → 弹窗里是文字      ✓
再复制一次图片  → 弹窗里没有缩略图  ✗
```

根因在 `resolveContent` 的取值链：

```
① 页面选中文字 → ② 剪贴板文字 → ③ 剪贴板图片 → ④ 页面标题+链接
```

第 ① 步看着最自然（"你选中的东西当然是你想发的"），但 **选中状态不会自己消失** —— 你右键复制完那段文字，高亮还挂在页面上。只要它还在，后面每一步都轮不到，刚复制的图片就被彻底跳过。

要命的那句区别是：**"选中文字"是页面上的一个持续状态，"复制到剪贴板"是一次动作。** 拿持续状态去压一个刚发生的动作，就会丢掉用户最新的意图。

修法：给两件事各记一个时刻，按**谁更新**判断，而不是按谁存在。

```js
selectionchange                     → window.__qqSendSelAt     // 选中文字变化的时刻
copy 事件里 types 含 image/*        → window.__qqSendImgCopyAt // "刚复制的是图片"
                                      （顺手把选中时刻作废）
```

两个时间戳挂在 `window` 上，后台注入的 `probePage()` 直接读得到 —— `chrome.scripting.executeScript` 注入的代码和 content script **在同一个 isolated world**（和 `qqImg` 取得到是同一个道理）。**读不到时（`imgCopyAt = 0`）按"图片优先"兜底**：剪贴板里冒出图片，本身就说明你刚复制了一张图。

另外两条配套改动：图片**不再被吃掉** —— 选中文字和图片两条都进候选（并写明"现在默认发哪一条"），点一下就能改选；图片的 `key` 从按位置算（`i:0`）改成按「体积 + 宽高」算，因为图片现在可能排在选中文字后面，位置不再稳定，照位置算会在"预览"和"发送"两次解析之间错位。

**已知残留边界（可接受）**：页面上留着选中文字、剪贴板里是**别处**复制的旧图、然后按 `Ctrl+B` 直接发 —— 这时会发那张旧图。要杜绝它就得知道"剪贴板到底是什么时候被写入的"，而 Chrome 不提供任何剪贴板变更通知，做不到。

判定逻辑本身写成了**可跑的断言**：自检脚本把 `background.js` 里那几行判定式**原样取出来**（`new Function`）跑四种输入组合。自己另抄一遍只能证明"抄对了"，取原文才能证明"代码是对的"。

### ⚠️ `storage.session` 的配额是「整次写入作废」，而且我们曾经静默挨着（`1.0.2` 补的两道防线）

`chrome.storage.session` 的 `QUOTA_BYTES = 10,485,760`（**官方文档核实过**，不是估的）。要紧的不是这个数字，而是它的失败方式 —— 官方原文：*updates that would cause this limit to be exceeded **fail immediately***，而 `set` 每次都是**覆盖整个键**。所以超限不是"这一条存不进去"，而是**这一次写入整体作废**：从那以后所有内容都不再进历史。

而当时那道门**一行代码都没守**：`pushHistory()` 把整段原文直接塞进去（`HISTORY_MAX = 4` 只管条数、不管每条多大），`writeStore()` 则是个 `catch (e) { /* 忽略 */ }`。配额一爆，你的体感只会是"候选列表怎么一直是这几条"/"怎么啥都没有"，**没有任何线索指向配额**。

**1.0.1 那次只堵了一半**：算出"4 张 2MB 截图 base64 后是 10.7MB"之后做了"图片不进历史"，图片这条路确实封死了。但**同一类失败换了个形式还敞着** —— 剩下的入口是**一条超大文本**，而且撞线所需的东西讽刺地从后门绕了回来：

- 从地址栏 / 编辑器复制一个 **`data:image/png;base64,…` 地址** —— 那串是纯文本、几 MB，正好从"图片不进历史"那道墙外面走过去
- 从 DevTools 复制大 JSON、日志；复制整篇超长文档或整页源码

算式也要跟着改：**不需要 4 条都大，一条超 10MB 就够。**

补的两道（都在 `extension/background.js`）：

| 防线 | 做法 | 数字 |
|---|---|---|
| ① 入口拦 | `STORE_ITEM_MAX = 512 * 1024`，单条超了就不进历史 | 4 条最多 **2MB = 配额 20%**，留 80% 余量 |
| ② 失败自愈 | 写入逐级退让：**4 → 2 → 1 → 空**，并把原因记进 `storeWarn`/`storeSkip` 带回弹窗 | 最坏是"历史只剩最新那条"，不再是"整条链断掉还查不出原因" |

三个实现细节值得记下来：

- **判大小必须按 UTF-8 字节算**（`new TextEncoder().encode(t).length`），中文一个字 3 字节 —— 用 `.length` 会低估三倍，而配额是按字节算的。
- **"只读"也要走那条串行链**（`return await editStore((st) => st.items)`）：`storeChain` 是为了防并发"读-改-写"互相覆盖，绕过它去读有可能读到写一半的状态。
- **退让后要以"真正写进去的"为准**：`editStore` 原本返回 `fn` 的结果，而退让发生在 `writeStore` 里 —— 不处理的话这一轮会多报一条候选，"点得动、但下次刷新就没了"。现在比较两者长度，砍短了就返回实际写进去的。
- **提示刻意不落进 `storage`** —— 那正是写不进去的地方，所以只在 service worker 内存里放着，随 `get-preview` 带回弹窗（底部红字一行，正常时是空串、不显示）。

验证方式沿用"取原文"那一套：`tools/test_quota_guard.js` 从 `background.js` 里把「存储 + 历史」那一段**切出来**，配一个**会按字节上限抛错**的假 `chrome.storage.session`（行为对齐 Chrome：整次写入抛错）跑 20 项 —— 含"正常文字不受影响""超大被挡下但既有的三条不被连坐""真撞配额时自动砍短""连一条都写不进去时不卡死、限额恢复后能重新写入""台阶不会重复试同样的大小"。

> 写这个假存储时踩了一次：`get` 要返回 `{ 键: 值 }`，而 `set` 收到 `{ 键: 值 }`、桶里只留"值"。第一版套了两层，导致"三条都进了历史"**假失败**了一轮 —— 测试的假实现写错，会比没测更容易让人误判。

### ⚠️ 站点能从**外面**把剪贴板关掉，而那条报错 `try/catch` 接不住（`1.0.3`）

现象：在 reverso.net 上，扩展的「错误」页里刷着

```
Permissions policy violation: The Clipboard API has been blocked because of
a permissions policy applied to the current document.
```

堆栈指向 `content.js` 里读剪贴板那一行 —— 而这个站点本身跟剪贴板毫无关系。

两点认知：

1. **根因在"别人家的房间"里。** Permissions Policy（旧名 Feature Policy）的 `clipboard-read`，默认白名单是 `self` —— 也就是说**跨域 iframe 里默认就是关的**（Chrome 的默认收紧，不需要站点特意去配）。而 `content_scripts` 开着 `all_frames: true`，`content.js` 因此也在那些 frame 里跑，每 2 秒读一次剪贴板 → 每 2 秒撞一次。reverso.net 只是恰好有这种 iframe（广告位、嵌入组件都能触发）。
2. **这条报错不是 Promise 的 rejection —— 它是浏览器自己往控制台打的。** `try/catch` 接不住它，`catch (e) { /* 忽略 */ }` 也接不住。所以唯一干净的解法是**先问策略、再决定叫不叫**：

   ```js
   var fp = document.permissionsPolicy || document.featurePolicy;
   return fp.allowsFeature('clipboard-read') !== false;   // 问不出来就放行
   ```

   （这两个名字都探：`document.permissionsPolicy` 是新名，但**实测在 Chromium 138 和 151 上它都是 `undefined`** —— 现在还只有旧名 `document.featurePolicy` 真正存在，所以两个都得留着。）

配套的三条设计取舍：

- **问不出来一律放行。** 老 Chrome、service worker 里没有 `document`、取策略时抛异常 —— 全是 `return true`。宁可多试一次（外层本来还有 `try/catch` 兜底），也不要把一个本来能用的页面误判成不能读。
- **弹窗那一侧刻意不设这道岗。** 它不受站点策略管（扩展页面的策略由我们自己的 manifest 决定），而它偏偏是唯一可靠能读到剪贴板的一条路 —— 在那里多拦一道，只会多一个"误拦"的风险。
- **还得有自愈。** 探测覆盖的是"我能想到的情形"，万一还有想不到的：`content.js` 认出策略类报错（`/permissions? policy|feature policy|disabled in this document/i`）后**永久闭嘴**，否则它会每 2 秒往错误页里刷一条。⚠️ 匹配串**刻意只认"策略"字样**：`NotAllowedError` 还有另一种来源是 `Document is not focused`（"判断焦点"和"真正读"之间被抢走焦点），那是偶发、下次就好，把它误判成永久状况的代价是整页快照停摆。

验证：`tools/test_clip_policy.js` 把 `clipReadAllowed` 与 `looksLikePolicyBlock` **从真实源码里切出来**（按花括号配平）跑 20 项。判定的标准不是"函数返回了啥"，而是**假剪贴板有没有被调用** —— 被拦时 `readText` 必须 0 次，那才是浏览器不报错的真正原因。

### ⚠️「扩展启动本地程序」只有一条路，而且它的"登记位置"不能靠文档猜（`1.0.4`）

需求是"点一下就把桥拉起来"。先把边界钉死：

| 直觉上的做法 | 实际情况 |
|---|---|
| 扩展直接 `exec` 一个 .bat | ❌ 没有这种 API |
| 用文件选择框让用户选 `start_bridge.bat`，扩展记住路径 | ❌ 浏览器**拿不到真实路径**，`File` 对象只给 `C:\fakepath\xxx`（安全限制，无解） |
| 把路径存进 `storage` 再调用 | ❌ 存得下，但**没有"运行本地程序"这个 API**可调 |
| **Native Messaging** | ✅ 官方唯一通道：扩展跟一个"宿主程序"对话，由宿主去启动别的东西 |

于是链路成了：扩展 → `sendNativeMessage` → Chrome 按注册表找到宿主 → 宿主拉起桥。

**坑一：注册表路径随浏览器品牌变，"写两个位置就万无一失"是想当然。**

一开始按 Chromium 源码的印象写了 `Software\Chromium\…` + `Software\Google\Chrome\…`。后来把木木实际在用的 **Thorium（Chromium 138）** 的 `chrome.dll`（260 MB）全文搜了一遍 `NativeMessagingHosts`，只搜出**两条**路径字面量：

```
SOFTWARE\Thorium\NativeMessagingHosts        ← 它自己的
SOFTWARE\Google\Chrome\NativeMessagingHosts  ← 兜底
```

**根本没有 `Software\Chromium`。** 也就是说当时能通，全靠"Google\Chrome 兜底"这条运气 —— 一旦哪天兜底逻辑变了，表现就是"点了按钮没反应"，而扩展那边**一个错都不报**。

> 教训：**注册表位置不能靠文档猜**（各分支会把产品名换掉）。要么实测，要么直接从主程序里搜字符串 —— 后者的好处是可复核、可重复。这就是 `tools/probe-native-roots.py` 存在的理由：它把浏览器主程序里的路径字面量捞出来，和我们实际登记的位置做**差集**，缺一处就报 FAIL。换浏览器时先跑它。

另外两个白捡的发现：`--load-extension` 在 **Chromium 137+ 已被移除**（本机实测：带上它、并把 Playwright 默认追加的 `--disable-extensions` 排除掉，`chrome://extensions` 里依然是 0 个扩展），新的 CDP `Extensions.loadUnpacked` 域在 138 上也不可用（`Method not available`）—— 所以"自动化加载扩展 + 触发原生消息"这条路**走不通**，最后一跳只能手工验一次。`tools/test_native_host.py` 的 `[1b]` 因此改成**按浏览器自己的规则模拟查找**（顺序、清单字段逐条验），把手工验证的失败面缩到最小。

**坑二：宿主入口那个 `.bat` 是"一个字节都不能多说"的程序。**

宿主跟浏览器的通道就是 stdin/stdout，协议是「4 字节小端长度 + UTF-8 JSON」。往 stdout 多写一个字符（一句 `echo`、一行 `chcp` 的提示），整个协议就乱掉，而浏览器只会回一句 `native host has exited` 这种跟真实原因毫无关系的话。所以：

- `qq_host.bat` 里 `chcp 65001 >nul`（不重定向会打一行 "Active code page: 65001"）、不写任何裸 `echo`、出错只往日志文件写
- 批处理内容**必须纯 ASCII** —— cmd.exe 是按 OEM 代码页（本机 936/GBK）读批处理的，写中文进去就是乱码
- 批处理**用 CRLF 行尾** —— LF 对 `goto` / 标签这类结构不可靠
- `qq_native_host.py` 里 `serve()` 那条路上一句 `print` 都没有（只有手动 `--register` 的 `cli()` 才有），并且显式把 stdout 切成二进制模式（免得 CRLF 转换插一脚）
- 自检里对 stdout 做**逐字节**校验：必须正好是 `4 + len` 个字节

**坑三：Chrome 回完话就把宿主进程杀掉 —— 它拉起的桥必须能活下来。**

不然这个功能就是"点了没反应"。`tools/test_native_host.py` 的第 5 段专门验这个：让沙箱宿主真的拉起一个 stub，等宿主进程退出后**继续观察 5 秒**，确认 stub 还在干活（tick 还在涨）。同时也验了窗口确实**最小化**（`IsIconic`）且**没抢到前台焦点**（`GetForegroundWindow`），以及**含中文的路径能穿过 `cmd /d /s /c`**。

顺带一个量版式的教训：状态行只有 272px。启动过程中的"已等 N 秒"最初写在状态行里，实测**只剩 10px 余量**（字体一换就会掉成两行）→ 改成写在按钮上。量这个不能用肉眼，也不能直接量元素宽度 —— `#statusText` 是 `flex: 1`，它会自己撑满剩余空间，量出来永远是"刚好占满"，什么问题都发现不了。正确做法是另起一个 `white-space: nowrap` 的隐身元素量文字的自然宽度，见 `tools/measure-popup-row.py`。

### 桥窗口标题为什么交给 Python 设，而不是在 `.bat` 里 `title`（`1.0.5`）

标题要改成中文。最直觉的做法是在 `start_bridge.bat` 里写 `title 这是转发…` —— **不行**：批处理是按 **OEM 代码页**（本机 936/GBK）读盘解析的。文件存成 UTF-8 就会被按 GBK 解，中文必乱；要是为了它把整个文件存成 GBK，又跟仓库里其它文件（一律 UTF-8）不一致，编辑器随手一存就漂回去。

所以标题由 Python 用 **`SetConsoleTitleW`** 设 —— 参数走 UTF-16，跟代码页完全无关。`.bat` 里只留一个纯 ASCII 的兜底标题（万一 Python 压根没起来）。

⚠️ 这里有个断言够不着的盲区：`verify-extension.js` 只能断言**源码里**用的是宽字符 API，**证明不了窗口上真的没乱码** —— 而标题变乱码恰好是那种不看窗口就发现不了的静默错误。所以另配了 `tools/probe-console-title.py`：开一个替身控制台，在里面 `import` **真实的** `qq_bridge`、调**真实的** `set_console_title()`，然后从外面把窗口标题读回来逐字符核对（标题字符串不另抄一份 —— 抄一遍只能证明"抄对了"）。

顺带：**提权**启动的控制台，Windows 会在标题前面**自己**加一串「管理员: 」，那串是系统加的，去不掉，也不是我们标题的一部分。

### ⚠️「按 X 最小化到托盘」为什么做不到（`1.0.6`）

需求是"按下关闭键就缩到托盘，要完全关掉只能在托盘点"。**前半句做不到**，原因很硬：

- 控制台窗口**不属于我们的进程**，它属于 `conhost.exe`。而 **Windows 禁止跨进程安装窗口过程**：`SetWindowLongPtr(hwnd, GWLP_WNDPROC, ...)` 实测返回 `0`、`GetLastError()=5`（`ERROR_ACCESS_DENIED`）。既然改不了它的消息处理，就改不了 X 的行为；`SetConsoleCtrlHandler` 也救不了 —— 它给 `CTRL_CLOSE_EVENT` 的只是"几秒钟善后时间"，拦不住关闭。
- **但"改样式"是放行的**（只改一个字段 + 发 `WM_STYLECHANGED`）：实测清掉 `WS_SYSMENU` 生效（`0x14EF0000 → 0x14E70000`），标题栏的 X 就没了。跨进程 `ShowWindow` 同样正常。

所以走的是**等价路线**，而不是去和系统较劲：

**摘掉 X + 把窗口藏起来 + 挂托盘图标 → 退出只走托盘。**
"手滑关掉"这个可能性是被**消灭**的，不是被拦住的。

🔴 **顺序绝对不能反**：必须先确认 `Shell_NotifyIcon(NIM_ADD)` 成功，才去藏窗口 / 摘 X。反过来的话，万一托盘没起来（资源管理器异常、Explorer 重启……），用户既看不见窗口、又没有 X、也没有托盘 —— **彻底没有出口**。这条有专门的测试守着：`tools/test_tray.py` 第 3 段把 `_add()` 打桩成失败，断言窗口必须**仍然可见、X 必须还在**。

另外三个踩过的坑（都实测）：

- **`GetConsoleWindow` 在 `kernel32`，不在 `user32`**。想当然放 `user32` 会 `AttributeError`，而且它只会让托盘**静默起不来**（桥本身照跑），特别难查。
- **窗口过程对象必须留引用**。它是 ctypes 回调，被 GC 掉之后系统再来消息就是**直接崩进程**。
- **窗口过程里调 `DefWindowProcW` 必须声明 `argtypes`**。否则 64 位下 LPARAM 溢出抛 `ArgumentError: argument 4: OverflowError: int too long to convert`，而 ctypes 会把它**静默吞掉、只打到 stderr** —— 表面现象是"什么都没发生"。

顺带一条好用的推论：**托盘图标消失 ≈ 桥进程没了**（Windows 会自动清掉死进程留下的图标）。所以"图标在不在"本身就是一个状态指示。

### 其它

- **Chrome 扩展目录里不能有下划线开头的文件**。`_` 是 Chrome 系统文件保留前缀，任何 `_xxx` 文件都会导致整个扩展**加载失败**，且报错信息误导性地显示为"无法加载清单"。
- **读剪贴板必须在「当前持有焦点的那个 document」里做** —— 本项目踩得最久的一个坑。Chrome 规定 `navigator.clipboard.readText()` 只能在有焦点的 document 里调用，否则抛 `NotAllowedError: Document is not focused.`；而 **offscreen 文档是隐藏的、永远拿不到焦点**（即使以 `reasons: ['CLIPBOARD']` 创建也一样），所以放进去读**必然失败**。正确做法是交给当时真正持有焦点的上下文：点图标时弹窗有焦点 → 由 `popup.js` 读；按快捷键时页面有焦点 → 由 `chrome.scripting.executeScript` 注入页面的脚本读。
- **读剪贴板失败时绝不能静默降级**。早期版本把失败吞掉、悄悄改发「页面标题+链接」，结果是：腾讯接口返回 200、图标跳绿色 OK、你以为什么都对了，而手机收到的其实是完全不相干的内容。现在失败原因会原样显示在弹窗里（连"弹窗读失败的原因"和"页面读失败的原因"分别列出来）。
- **content script 在隔离世界里照样能收到 DOM 事件**。`document.addEventListener('copy', ...)` 拿得到，且能用 `window.getSelection().toString()` / `e.clipboardData.getData('text/plain')` 读出内容。从 content script 发 `chrome.runtime.sendMessage` 时**要带一个空回调**去消费 `lastError`，否则扩展刚重载过时控制台会刷红字。
- **`chrome.scripting.executeScript` 注入的函数会被序列化**，必须自包含、不能引用外部变量；内部要吞掉所有异常，否则注入失败会被误判成"页面受限"。
- **不申请 `tabs` 权限**（免得弹"读取您的浏览记录"）：页面标题和 URL 一律靠 `chrome.scripting.executeScript` 在页面内取。`activeTab` 权限在快捷键触发时同样会被授予。
- **未打包扩展的默认快捷键不会自动生效**，必须去 `chrome://extensions/shortcuts` 手动设一次。
- **加了 host 权限后，已打开的标签页要刷新**，新的 content script 才会注入进去。
- **`navigator.clipboard.readText()` 读不出剪贴板里是不是图片** —— 剪贴板装图片时它和"真的空着"返回的都是空字符串。要分辨得额外调 `navigator.clipboard.read()` 列举 `item.types`（只列类型，不读图片数据，很轻）。本项目**只在读出空的时候**才走这一步，不做无谓开销。
- **截断中文/emoji 要用 grapheme 而不是 `.slice()`**。`.slice()` 按 UTF-16 码元切，会把 emoji 劈成半个、显示成乱码方块。本项目用 `Intl.Segmenter`（按"人眼看到的一个字"切），并保留 `Array.from()` 兜底。
- **Chromium/Electron 应用默认不构建无障碍树**。要先打开 Windows 的"读屏软件正在运行"标志（`SPI_SETSCREENREADER`），UI Automation 才能读到 Electron 应用的 DOM 结构 —— 这是 `tools/probe_uia*.py` 能跑通的前提。
- **代理的 fake-IP 模式可能干扰 Python 直连**。`tools/net_check.py` 会验证域名是否解析到真实 IP。
- ⚠️ **含中文的 `.ps1` 脚本必须存成「UTF-8 带 BOM」**，否则 Windows PowerShell 5.1 会按**当前代码页（本机是 GBK）**去解码，中文注释全变乱码，还会连带把引号/花括号解错，报一堆莫名其妙的 `Missing closing '}'`、`The string is missing the terminator`。`tools/make-release-package.ps1` 就踩过这个 —— 它明明语法正确，却完全无法执行。补 BOM 一行搞定：

  ```powershell
  $t = [System.IO.File]::ReadAllText($p, (New-Object System.Text.UTF8Encoding $false))
  [System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding $true))
  ```

  改完 `.ps1` 顺手做个真语法检查，别靠肉眼：
  ```powershell
  $e = $null
  [System.Management.Automation.Language.Parser]::ParseFile($p, [ref]$null, [ref]$e)
  if ($e.Count) { $e | ForEach-Object { $_.Message } } else { 'PARSE_OK' }
  ```
- ⚠️ **打 zip 的脚本，复检路径要多算一层**。`Compress-Archive -Path <文件夹>` 会把**该文件夹本身**放进 zip 顶层，所以"解压回来检查文件是否齐全"时，路径是 `解压根\包名\文件`，不是 `解压根\文件`。漏算这层会让齐全性检查**全部误报缺失**（`make-release-package.ps1` 第一版就是这么错的）。
